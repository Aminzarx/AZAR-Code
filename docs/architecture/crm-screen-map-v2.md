# AZAR CRM — Screen Map v2 (بر اساس معماری پیشنهادی)

**مبنا**: `crm-architecture-audit-v1.md`. تصمیم‌های `PRODUCT DECISION
REQUIRED` آن سند که هنوز پاسخ صریح نگرفته‌اند، اینجا با **پیش‌فرض‌های
پیشنهادی همان سند** جلو رفته‌اند (مشخص‌شده با 🔸) — یعنی هنوز قابل
تغییرند، رد نشده‌اند. طبق Rule 10، این سند مستندسازی است، نه کد؛ کد
هنوز تغییر نکرده.

فرمت هر صفحه طبق §35: Route / Purpose / Entry / Exit / Components /
Data Source / Actions / Validation / Loading / Empty / Error /
Permissions / Business Rules / Navigation / Related Entities. مختصات
تقریبی UI (مثل سند قبلی `app-screen-map.txt`) فقط جایی که واقعاً چیز
تازه‌ای می‌گوید تکرار شده — برای صفحات بدون تغییر بصری اساسی، فقط تغییر
منطقی/دیتا مستند شده.

---

## نوار پایین (تغییر یافته) 🔸

طبق پیشنهاد گزینه‌ی ۲ در بخش H سند معماری:

```
خانه | پرونده‌ها (Property+Contact+CustomerNeed) | تطبیق | پیگیری‌ها (Deal) | پروفایل
```

«قراردادها» به‌عنوان تب مستقل حذف می‌شود؛ Contract از داخل صفحه‌ی
جزئیات Deal قابل دسترس است (چون هر Contract همیشه از یک Deal می‌آید).
لیست کامل قراردادها (برای جست‌وجوی مستقیم) از طریق یک دگمه‌ی «همه‌ی
قراردادها» در بالای تب «پیگیری‌ها» در دسترس می‌ماند — تا چیزی از دست
نرود، فقط ورودی اصلی عوض می‌شود.

---

## ۱. مخاطبین (Contact) — بخش تازه 🔸

**تصمیم ناوبری** (بخش G سند معماری، پیشنهاد پیش‌فرض): زیر تب «پرونده‌ها»،
گزینه‌ی سوم در Segmented Control موجود («املاک / متقاضیان / مخاطبین»).

### ۱.الف لیست مخاطبین
- **Route**: `ContactList` (زیرمسیر تب Files)
- **Purpose**: مرور همه‌ی اشخاص سیستم (مالک، خریدار، مستأجر، معرف، همکار...)
- **Entry**: Segmented Control در Files؛ از دکمه‌ی «افزودن مالک» هنگام ساخت Property
- **Exit**: `ContactDetail`, `CreateContact`
- **Components**: `TextInput`(جستجو: نام/تلفن) + چیپ‌های فیلتر نقش (Owner/Buyer/...) + `FlatList` از `ContactListItem`
- **Data Source**: `ContactRepository.search(orgId, query, roleFilter?)`
- **Actions**: جستجو، فیلتر نقش، لمس → جزئیات
- **Loading**: `LoadingIndicator size="large"`
- **Empty**: «هنوز مخاطبی ثبت نشده. اولین مالک یا مشتری خود را اضافه کنید.» + دگمه‌ی «افزودن مخاطب»
- **Error**: `ErrorState` + تلاش مجدد
- **Permissions**: MVP تک‌کاربره → بدون محدودیت؛ فیلد آماده برای Phase 2 (assignedTo)
- **Business Rules**: —
- **Related Entities**: Property(owner)، CustomerNeed، Deal، Reminder، Activity

### ۱.ب افزودن/ویرایش مخاطب
- **Route**: `CreateContact` / `ContactDetail` (edit mode)
- **Components**: فیلدهای «نام و نام خانوادگی»*، «شماره تماس»*، چک‌باکس‌های چندگزینه‌ای نقش (Owner/Buyer/Tenant/Seller/Landlord/Agent/Referrer/Collaborator — حداقل یکی الزامی)، «یادداشت» اختیاری
- **Validation**: نام و تلفن الزامی؛ تلفن باید فرمت موبایل ایران معتبر باشد (نه فقط «حداقل ۸ رقم»)؛ حداقل یک نقش انتخاب شود
- **Business Rules**: BR (جدید) — یک Contact نمی‌تواند بدون هیچ نقشی ذخیره شود
- **Duplicate Detection**: قبل از ثبت، اگر تلفن از قبل موجود بود: «این شماره قبلاً برای «{نام}» ثبت شده — همان مخاطب را باز می‌کنید یا ادامه می‌دهید؟» (§20)

### ۱.ج جزئیات مخاطب
- نام، تلفن، نقش‌ها (چیپ)، یادداشت
- **بخش‌های مرتبط** (تب‌های داخلی یا آکاردئون): املاک تحت مالکیت او، نیازهای معاملاتی مرتبط، معاملات (Deal) مرتبط، یادآوری‌های مرتبط، Timeline فعالیت (Activity)
- دگمه‌ی «ویرایش»، دگمه‌ی «آرشیو» (Soft Delete، نه حذف فیزیکی — طبق BR-007)

---

## ۲. پرونده‌ی ملکی (Property) — بازطراحی‌شده

### ۲.الف افزودن/ویرایش ملک
تغییرات نسبت به فرم فعلی:
- «نوع معامله» و «قیمت» از این فرم **حذف** می‌شوند (به فرم Listing منتقل
  می‌شوند — بخش ۳).
- فیلد «مالک» اضافه می‌شود: Autocomplete روی Contactهای با نقش Owner؛
  اگر مالک هنوز ثبت نشده، دگمه‌ی «+ مالک جدید» همان‌جا `CreateContact`
  را به‌صورت مینی‌فرم (نام+تلفن) باز می‌کند تا کاربر مجبور به ترک فرم
  ملک نشود.
- فیلدهای باقی‌مانده: عنوان*، نوع ملک (Autocomplete)، شهر* (Autocomplete)،
  آدرس*، متراژ، تعداد اتاق (کنار هم، FormRow)، توضیحات.
- **Validation**: عنوان/شهر/آدرس/مالک الزامی.
- بعد از ثبت Property موفق: کاربر مستقیم به فرم «افزودن آگهی (Listing)»
  هدایت می‌شود (چون یک Property بدون حداقل یک Listing عملاً در Matching
  دیده نمی‌شود) — با دگمه‌ی «فعلاً بدون آگهی» برای رد کردن این قدم.

### ۲.ب جزئیات ملک
- عنوان، مالک (لمس‌پذیر → ContactDetail)، شهر/آدرس، متراژ، اتاق، توضیحات
- **بخش «آگهی‌ها» (Listings)**: لیست همه‌ی Listingهای این Property
  (می‌تواند چند مورد باشد) — هرکدام: نوع معامله + قیمت/ودیعه+اجاره +
  وضعیت + دگمه‌ی «پیشنهادهای تطبیق» مخصوص همان Listing
- دگمه‌ی «+ افزودن آگهی جدید»
- دگمه‌ی «ویرایش پرونده»، «آرشیو ملک»

---

## ۳. آگهی (Listing) — Entity تازه 🔸

### ۳.الف افزودن/ویرایش آگهی
- **Route**: `CreateListing` (پارامتر: `propertyId`) / ویرایش داخل جزئیات ملک
- **Components**:
  - «نوع معامله» (Autocomplete: فروش/اجاره/رهن‌و‌اجاره) *
  - اگر «فروش»: فیلد `MoneyInput` «قیمت کل»
  - اگر «اجاره» یا «رهن‌و‌اجاره»: دو فیلد کنار هم (FormRow) «ودیعه» و
    «اجاره ماهانه» (هر دو `MoneyInput` با چیپ‌های سریع صفر)
  - «وضعیت آگهی» (Segmented: پیش‌نویس/فعال/متوقف)
- **Validation**: بسته به نوع معامله، فیلد قیمت متناظر الزامی (BR جدید:
  «فروش» بدون قیمت کل، یا «اجاره» بدون حداقل یکی از ودیعه/اجاره، ثبت
  نمی‌شود)
- **Business Rules**: BR-008 (آگهی نمی‌تواند فعال شود اگر Property
  آرشیو باشد)
- **Related Entities**: Property (parent)، Match/Deal (children)

## ۴. نیاز معاملاتی مشتری (CustomerNeed — جایگزین Applicant)

فرم و جزئیات تقریباً همان فرم فعلی Applicant است، با این تفاوت‌ها:
- «نام و نام خانوادگی» و «شماره تماس» از این فرم **حذف** می‌شوند (چون
  این‌ها حالا متعلق به Contact هستند، نه CustomerNeed مستقیم).
- در جای آن، فیلد «مشتری» اضافه می‌شود: Autocomplete روی Contactهای
  نقش Buyer/Tenant؛ همان الگوی «+ مخاطب جدید» مثل بخش ۲.الف.
- فیلد «اولویت» (کم/متوسط/زیاد) اضافه می‌شود — چیپ‌های سه‌گزینه‌ای.
- بقیه‌ی فیلدها (نوع معامله مدنظر، نوع ملک مدنظر، شهر، بودجه، متراژ،
  تعداد اتاق، توضیحات) **بدون تغییر** می‌مانند (Autocomplete/MoneyInput/
  FormRow که در فاز قبلی ساخته شده‌اند، مستقیم reuse می‌شوند).
- **Validation**: BR-001، BR-002 (بدون تغییر) + مشتری الزامی.

جزئیات: مشتری (لمس‌پذیر → ContactDetail) + بقیه‌ی فیلدها + بخش
پیشنهادهای تطبیق (بدون فیلتر سخت شهر — بخش ۶).

## ۵. Dashboard (توسعه‌یافته)

تغییرات نسبت به نسخه‌ی فعلی («Minimal Luxury» بصری بدون تغییر، فقط
منبع/محتوای داده):

| بخش | وضعیت فعلی | تغییر |
|---|---|---|
| هدر (آواتار+خوش‌آمد+کد معرف) | بدون تغییر | — |
| ۴ کارت آماری | بدون تغییر بصری | داده از Property/CustomerNeed/Deal/Contract فعال می‌آید (بدون تغییر منطقی) |
| **بخش تازه: «امروز»** | وجود ندارد | کارت‌های کوچک: یادآوری‌های امروز، Overdue (برجسته با رنگ `warning`/`error`)، بازدیدهای امروز (اگر Visit فعال شد) |
| **بخش تازه: «Pipeline»** | وجود ندارد | ردیف افقی از تعداد Dealها به تفکیک Stage (۸ عدد کوچک، بدون نمودار پیچیده — طبق §33 سادگی) |
| اقدامات سریع | بدون تغییر بصری | گزینه‌ی «افزودن متقاضی» → «افزودن نیاز مشتری» تغییر نام می‌کند؛ آیکون‌ها ثابت |
| Timeline فعالیت‌های اخیر | از قبل موجود | منبع داده از Activity Log واقعی می‌آید (نه فقط created_at خام) |
| یادآوری‌های نزدیک | بدون تغییر | — |

## ۶. تطبیق (Matching) — بازطراحی‌شده

### تغییر UX (طبق §29)
به‌جای Segmented Control خام «املاک / متقاضیان»:

```
عنوان: «چه چیزی می‌خواهید پیدا کنید؟»

[ کارت بزرگ: مشتری برای یک آگهی ]
[ کارت بزرگ: آگهی برای یک مشتری ]
```

هرکدام یک کارت تمام‌عرض با آیکون + عنوان + توضیح یک‌خطی، نه صرفاً دو
دکمه‌ی کوچک — چون این تصمیم مسیر کل صفحه را عوض می‌کند و باید واضح‌تر
از یک Segmented Control معمولی باشد.

با انتخاب هرکدام → لیست Listingها یا CustomerNeedها (بدون فیلد جستجو،
مثل الان) → لمس یک مورد → صفحه‌ی نتایج تطبیق همان مورد.

### صفحه‌ی نتایج تطبیق (بازطراحی منطقی، نه بصری)
- هر نتیجه: عنوان طرف مقابل + Score (٪) + بج‌های ✓/△ برای معیارهای
  matched/mismatch (بخش F.4 سند معماری) + دگمه‌ی «ایجاد پیگیری»
- **حذف فیلتر سخت شهر** (BR-009): نتایج شهر متفاوت هم دیده می‌شوند، با
  Score پایین‌تر؛ 🔸 آستانه‌ی پیش‌فرض `minScoreToShow = 20` (نتایج زیر
  این آستانه اصلاً رندر نمی‌شوند، تا لیست شلوغ نشود)
- **Empty با آستانه**: اگر هیچ نتیجه‌ای بالای آستانه نبود: «هیچ تطبیق
  قابل‌توجهی پیدا نشد. معیارها را در نیاز مشتری/آگهی بازبینی کنید.»

## ۷. پیگیری‌ها (Deal) — بازطراحی‌شده، تب مستقل 🔸

### ۷.الف لیست پیگیری‌ها
- **Route**: `DealList` (حالا مستقیم از نوار پایین)
- **Components**: فیلتر Stage (چیپ‌های افقی قابل‌اسکرول: همه/جدید/در
  تماس/بازدید/مذاکره/پیشنهاد/قرارداد/برد/باخت) + `FlatList`
- **Data Source**: `DealRepository.search(orgId, stageFilter?)`
- **Empty**: «هنوز پیگیری‌ای ثبت نشده. از صفحه‌ی تطبیق، یک پیشنهاد را
  به پیگیری تبدیل کنید.» + دگمه‌ی «رفتن به تطبیق»

### ۷.ب جزئیات پیگیری (بازطراحی)
| بخش | تغییر نسبت به فعلی |
|---|---|
| کارت «ملک» / «متقاضی» | عنوان به «آگهی» و «مشتری» تغییر می‌کند؛ محتوا مشابه |
| **نوار Stage جدید** | به‌جای چیپ‌های وضعیت ساده‌ی فعلی (۶ گزینه)، یک نوار افقی Stepper با ۹ مرحله (E.1) — لمس یک مرحله بعدی = انتقال رو-به-جلو؛ برای Lost یک دگمه‌ی مجزای قرمز «علامت‌گذاری به‌عنوان ناموفق» |
| **مودال Lost Reason** (تازه) | با لمس «ناموفق»، مودالی با لیست دلایل (چیپ انتخابی، طبق §11) باز می‌شود — بدون انتخاب دلیل، ثبت نمی‌شود (BR-004) |
| **بخش «Stage History» (تازه)** | Timeline کوچک زیر Stepper: هر تغییر مرحله با تاریخ |
| فیلد یادداشت + دگمه‌ی ذخیره | بدون تغییر |
| دگمه‌ی «افزودن یادآوری» | بدون تغییر |
| دگمه‌ی «ایجاد قرارداد» | بدون تغییر ظاهری؛ فقط اگر Stage هنوز به «قرارداد» نرسیده، یک هشدار ملایم (نه مسدودکننده مگر BR-010 تأیید شود) |
| **فیلد «ارزش تخمینی معامله» (تازه)** | `MoneyInput` اختیاری، برای گزارش Pipeline در Dashboard |

## ۸. قرارداد (Contract) — از داخل Deal، نه تب مستقل

### ۸.الف افزودن قرارداد (از دکمه‌ی «ایجاد قرارداد» در DealDetail)
تغییرات فرم:
- «نوع قرارداد» به «نوع معامله» تغییر می‌کند و **از Listing مرتبط
  پیش‌فرض پر می‌شود** (قابل تغییر دستی)
- بسته به نوع معامله:
  - فروش → فیلد «قیمت کل» (`MoneyInput`)
  - اجاره/رهن‌و‌اجاره → «ودیعه» + «اجاره ماهانه» کنار هم (FormRow)
  - (دقیقاً همان الگوی فرم Listing، تکرار عمدی چون ممکن است مبلغ نهایی
    قرارداد با مبلغ اولیه‌ی آگهی فرق کند — چانه‌زنی)
- «طرفین معامله»: دو Autocomplete روی Contact (خریدار/مستأجر از
  CustomerNeed پرشده، مالک/موجر از Property پرشده) — هر دو قابل تغییر
- ردیف کنار‌هم «تاریخ شروع» + «تاریخ پایان» (بدون تغییر)
- «یادداشت» (بدون تغییر)
- **Validation**: BR-005 (طرفین الزامی برای فعال‌شدن)

### ۸.ب جزئیات قرارداد
- بدون تغییر ظاهری اساسی؛ فقط نمایش مبلغ بسته به نوع معامله (قیمت کل
  یا ودیعه+اجاره) به‌جای یک عدد عمومی
- دگمه‌ی «آرشیو» به‌جای «حذف» (BR-007 — Soft Delete)

### ۸.ج لیست همه‌ی قراردادها (دسترسی جایگزین تب حذف‌شده)
- دگمه‌ی «همه‌ی قراردادها» بالای تب «پیگیری‌ها» → همان لیست فعلی
  Contract، بدون تغییر ساختاری

## ۹. یادآوری (Reminder) — توسعه‌یافته

- فرم افزودن: فیلد ارتباط اضافه می‌شود — Autocomplete روی
  «Contact/Property/CustomerNeed/Deal/Contract» (یک لیست انتخابی، نه
  همه هم‌زمان؛ کاربر یکی را به‌عنوان موضوع اصلی انتخاب می‌کند)
- **Status جدید** به‌جای فقط چک‌باکس ✓: نشان بصری رنگی — `pending`
  خنثی، `due_today` زرد (`warning`)، `overdue` قرمز (`error`)، `completed`
  خاکستری خط‌خورده (بدون تغییر عمده‌ی چیدمان فعلی، فقط رنگ نشان)
- Dashboard بخش «امروز» این وضعیت‌ها را برجسته می‌کند (بخش ۵)

## ۱۰. Auth / Profile — بدون تغییر معماری اساسی

فایل ورودی (§24) نکاتی درباره‌ی OTP/Phone خواسته که **Business Logic
است، نه UI** — پس در Screen Map تغییر ظاهری ندارد؛ فقط:
- `PhoneEntryScreen`: پیام خطای اعتبارسنجی از «حداقل ۸ رقم» به پیام
  دقیق‌تر («شماره موبایل معتبر ایران وارد کنید») تغییر می‌کند —
  Validation منطق در لایه‌ی Business Rule (Phase 3)، نه در این سند.
- بقیه (OTP ۶‌خانه‌ای، Profile/Settings، Logout confirmation) **بدون
  تغییر** — این‌ها از قبل با معماری جدید سازگارند.

## خلاصه‌ی صفحات جدید/حذف‌شده

| وضعیت | صفحه |
|---|---|
| **جدید** | ContactList, CreateContact, ContactDetail |
| **جدید** | CreateListing (زیرصفحه‌ی Property) |
| **بازنام‌گذاری** | Applicant* → CustomerNeed* (همان صفحات، منطق داخلی تغییر می‌کند) |
| **حذف از نوار پایین** | تب «قراردادها» (محتوا حذف نمی‌شود، مسیر ورود عوض می‌شود) |
| **بازطراحی محتوا (نه ظاهر)** | DealDetail (Stepper + Lost Reason + Stage History)، MatchingScreen (سؤال دوگزینه‌ای)، Dashboard (بخش امروز + Pipeline) |
